# Brahma Desk — Update Center Mini-Update

## 1. Overview

The Update Center provides an interface for checking for application updates and guiding the user through downloading and installing a newer version of Brahma Desk.

The intended distribution channel is GitHub Releases, using Electron's update infrastructure and `electron-updater`.

## 2. Intended user experience

The Update Center should communicate the current application version and update status clearly.

Expected interactions include:

1. Display the installed application version.
2. Allow the user to check for updates.
3. Show whether an update is available.
4. Display release notes when available.
5. Show download progress while an update is downloading.
6. Allow the user to initiate installation and restart when an update has been downloaded.
7. Display understandable errors when checking or downloading fails.

These are the intended behaviors. Each should be verified against the current implementation before being described as fully functional.

## 3. Components

The update flow involves the following areas:

- **Renderer UI:** The Update Center interface in the React application.
- **Electron main process:** Coordinates update checks, download events, and installation requests.
- **IPC bridge:** Exposes only the necessary update operations to the renderer.
- **`electron-updater`:** Handles update metadata, downloads, and installation integration.
- **GitHub Releases:** Hosts published installers and update metadata.

The Electron main process should remain responsible for privileged update operations. The renderer should not receive unrestricted Node.js access.

## 4. Publishing configuration

The Electron application's `desktop/package.json` should use the correct GitHub repository:

```json
{
  "publish": [
    {
      "provider": "github",
      "owner": "Darshan-U-P",
      "repo": "BrahmaDesk",
      "releaseType": "release"
    }
  ]
}
```

Merge this configuration into the existing `build` configuration rather than replacing unrelated settings.

The repository is:

https://github.com/Darshan-U-P/BrahmaDesk

## 5. Release assets

A Windows release using the NSIS installer target is expected to publish:

- The versioned Windows installer, such as `BrahmaDesk-Setup-0.1.1.exe`.
- `latest.yml`, containing release metadata and installer information.
- Any additional metadata or block-map files generated by the configured builder.

The exact filenames depend on the existing Electron Builder configuration.

## 6. Versioning and release process

For each release:

1. Update the application version in `desktop/package.json`.
2. Review and test the changes.
3. Build the frontend and packaged backend as required.
4. Build the Windows installer.
5. Publish the installer and update metadata to GitHub Releases.
6. Verify the release assets and release notes.
7. Test update detection from an older installed version.

For example, testing an installed `0.1.0` build against a published `0.1.1` release provides a basic update scenario.

## 7. Credentials

Publishing to GitHub may require a suitable GitHub token.

- Store the token in a temporary environment variable for the publishing session.
- Never commit the token to Git.
- Never include it in frontend source code, logs, screenshots, or release assets.
- Use the minimum repository permissions required.
- Do not assume that a successful local build means publishing succeeded.

## 8. Installation and user control

The application should clearly distinguish checking, downloading, and installing an update.

Do not restart or install unexpectedly while the user is working. Present an explicit install/restart action and communicate the consequences.

## 9. Validation checklist

- [ ] The application reports its current version correctly.
- [ ] Checking for updates reports errors clearly.
- [ ] An available release is detected.
- [ ] Release notes are displayed when available.
- [ ] Download progress is displayed.
- [ ] Download failures are handled.
- [ ] The user can initiate installation and restart.
- [ ] The packaged application can access the update service.
- [ ] A real older installation successfully detects a newer release.

## 10. Limitations

Update availability depends on correct publishing configuration, a compatible packaged application, valid release metadata, network access, and the target platform.

Do not treat a visible Update Center or a successful development build as proof that production updates work. Verify the full flow using a packaged installation.
